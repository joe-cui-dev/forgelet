# Durable Memory is Supplied by In-Session Capture

ADR 0064 diagnosed Durable Memory's failure as supply rather than selection. ADR 0075 bet that the missing supply was a model deriving conventions from friction, and its own evaluation falsified the bet: a batch produced 17 Memory Suggestions from 6 Sessions and zero were accepted, while the only Durable Memory that exists — the two entries in `.forgelet/memory.md` — was typed by hand. Reviewed by content the 17 hold two durable conventions against fifteen restatements and defect reports, below the criterion's threshold of three (see ADR 0075's retreat record). The two hand-written entries are the highest-quality entries in the corpus. The evidence points one way: the human wording was never the bottleneck the model was hired to solve.

So the producer changes from model to human, and nothing else does. Friction detection survives unchanged — detection was never what failed, and the Friction Signal is still the sharpest deterministic marker of where a Session met the workspace and lost. What changes is what friction triggers: instead of gating a Retrospective Session that derives conventions, it gates a prompt at Session end that shows the human where the friction was and asks them to write the entry, if there is one worth writing. The slogan the design settled on: retrieval belongs to the machine, wording belongs to the human. A captured line becomes a Memory Suggestion with the same schema-v1 Provenance Snapshot a derived one carried, and flows through the same deterministic, model-free Project Memory Review chain (`forge memory list/show/accept/reject`) untouched. The only edit to that chain is flattening the Rendered Memory Block to a single bullet with trailing provenance (WP7 from ADR 0075's consequence list), done now because the Memory Decision Log is still empty and byte identity is free to move only while it stays empty.

The real bottleneck is remembering to write, not writing. This is why the prompt is the primary mechanism and a bare `forge memory add` is only a fallback: a human who has to recall, unprompted, that a wall they hit an hour and several hundred Trace lines ago was worth recording will not do it, but a human shown that wall at the moment the Session ends might. The prompt fires only when the Session carried at least one Friction Signal — measured at roughly 1 Session in 12 — so it stays rare enough to answer rather than dismiss.

## Consequences

- The Retrospective Workflow (`src/workflows/retrospective.ts`), the `forge memory suggest` / `--all` CLI surface, and their tests are deleted. `src/memory/frictionSignal.ts` stays: friction detection is reused as the prompt gate.
- No deduplication logic is added. Duplicates in the derived pool existed only because nothing was ever accepted; a human producer who is shown the current Durable Memory does not restate it, and the Retrospective prompt's dedup step disappears with the workflow.
- `accept` stays binary — no edit-at-accept. Rewording a captured entry goes through editing `.forgelet/memory.md` directly, which is a user-editable file by definition, or reject-and-recapture.
- When stdin is not a TTY — Background Sessions, pipes, smoke tests — the capture prompt never blocks. The Session's friction points are printed into its final output so the human can backfill later with `forge memory add --session <id> "..."`.
- The ROADMAP claim that Memory Suggestions produced by background Sessions land in the Decision Queue no longer holds: capture produces a suggestion only when a human writes one, and a completed Background Session prints its friction and moves on rather than queueing anything.
