# The Wrap-Up Turn Keeps Its Cached Prefix

ADR 0029 reserved a `finalOnly` turn and described it as tool-free, and the loop of that era sent it with no tool schemas at all. Because the request carried no tools, the historical assistant/tool protocol left in the conversation read to DeepSeek as an invitation to keep calling them, and it answered in tool-call markup instead of prose. The fix then was to flatten the conversation: every `tool` message rewritten to a `user` message reading `Earlier tool observation: …`, every tool-call-only assistant message dropped.

The premise has since gone. The wrap-up turn now **keeps** the schemas and is held back by `tool_choice: "none"`, precisely so it does not invalidate the prompt prefix the Session has spent every prior turn building — the reasoning is already recorded on `TurnPlan.offerTools`. But the flattening stayed, and it rewrites messages from the first observation onward, so the prefix it was preserving died one line later anyway. `sess_msbodxyw` is the receipt: fourteen turns cached between 70% and 90% of their input, then the wrap-up turn read 61,085 tokens with **zero** cache hits and cost $0.0102 — 22% of the whole Session, for one turn that called nothing.

So the flattening now applies only when the request carries no schemas. `tool_choice: "none"` is the stronger guard and the free one: it forbids the calls at the API level rather than by hiding the evidence that they happened, and it touches no byte of the prefix. The Sessions still reaching the flattening path have no prefix to lose — an `answer_once` policy never ran a tool turn, and a Session whose first turn is also its last has nothing behind it — which is what makes the trade safe to keep making there and wrong to make anywhere else.

The backstop is unchanged and is what makes this cheap to be wrong about: tool calls returned on a wrap-up turn are blocked without execution, and the closing content that arrives beside them is still kept.
