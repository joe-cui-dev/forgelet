# Estimated Cost Is Priced at the Provider's Timestamp

DeepSeek had long advertised a peak-hour surcharge without saying when peak hours were, so ADR 0058's cost budget ran against a single rate set and a `timeOfDayPricing: "undated_peak_hours_2x"` marker that recorded the gap; CONTEXT.md accordingly declared estimated cost a lower bound whenever a Profile's time-of-day policy had an unknown effect. On 2026-08-17 the gap closed: DeepSeek published explicit windows — 01:00–04:00 and 06:00–10:00 UTC, with off-peak rates exactly half the peak rates — alongside a general increase that roughly doubled every published figure. We decided to make estimated cost time-of-day aware rather than keep pricing at one rate, and to delete the "unknown time-of-day effect" concept entirely instead of retaining an unused variant against a future repeat. A Model Profile now stores only the off-peak rates and derives peak by doubling, so "off-peak is half of peak" stays an invariant in one place rather than a coincidence two hand-maintained tables must keep agreeing on. We rejected storing both rate sets verbatim, which is faithful to the docs' layout and wrong the first time someone updates one column.

A turn is priced at a single instant, and that instant is the provider's own `created` stamp — already on every Chat Completions response and repeated identically across the chunks of a streamed one, from which we keep the first. The windows are facts about DeepSeek's clock, so classifying them with the caller's clock would make local skew a silent mispricing of every turn landing near a boundary; the local clock remains the fallback when `created` is absent, which costs nothing away from a boundary. We rejected prorating a turn that straddles a boundary across both rates: DeepSeek does not publish which timestamp it bills on, we do not know how a turn's tokens distribute across its own duration, and inventing that distribution would be precision we have not earned. Charging a straddling turn entirely at the peak rate was rejected for a sharper reason — it would bias the estimate upward, inverting the direction of the lower-bound guarantee that unpriced turns still carry. The residual error is therefore one boundary-straddling turn per Session at worst, in either direction, rather than a systematic bias.

Because cost is no longer a function of token counts alone, a Trace that records only tokens cannot explain why one Session cost twice another. Each turn's usage therefore records its **Pricing Window**, which rides the existing `ModelUsage` into the Trace and lets `forge explain` count peak-priced turns. We kept that aggregate derived rather than adding a field to `BudgetUsage`, which would have persisted through Pause Snapshots and the resume path a number any Trace reader can count. The window is deliberately *not* surfaced in Turn Status: ADR 0058's invariant exists so a Session never dies against a wall the model could not see and plan around, and the model already sees the cost figure — it has no action that reschedules its own Session, so the window would be prompt bytes it cannot act on. The person launching the Session does have that action, and only before the first turn, so the CLI prints a pre-launch notice naming when the current peak window closes; "you are in peak hours" without a closing time gives no way to judge whether waiting is worth it. The default cost budget moves from $0.15 to $0.35, recalibrating what one Session buys against the new off-peak rates that cover 17 of every 24 hours; a Session in a peak window buys about half that and wraps up sooner, which is the budget reporting a genuinely more expensive hour rather than a regression. Sessions paused before the change and resumed after it keep their accumulated cost as recorded, mixing old and new rates under one limit — ADR 0058 already settled that old Traces are honest history, and retroactively repricing them would be a fabrication of a different kind.
