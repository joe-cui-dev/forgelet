# Page Conversations are Promoted Whole into One Knowledge Note

The Browser Workbench was a dead end for its own output. A Page Conversation reads a page, delivers a Page Brief, and answers follow-ups grounded in the capture — and then evaporates. Nothing it produces reaches the Knowledge Library, so a user who wanted to keep what they learned had to leave the Side Panel, find the Session id in the terminal, and run `forge notes create`. The gap this ADR closes is the exit: a completed Page Conversation can now be promoted, in one click, into a single Knowledge Note, with the same capability exposed on the CLI as `forge notes create --from-conversation <conversationId>`.

The unit of promotion is the whole conversation, not a piece of it. A Page Conversation is already a linear chain — the root Page Brief plus every successfully completed follow-up Page Answer — and that chain is the artifact worth keeping; the root Brief alone loses the reasoning the follow-ups added, and the head Answer alone is unreadable without the Brief it built on. So the Note body is the root's `Summary`/`Key Concepts` followed by a section per follow-up carrying the question, the `Answer`, and the `Evidence` verbatim. Evidence is kept, not dropped: the excerpts are what make an Answer checkable against the capture, and a Note that discards them keeps the claim and throws away the proof. The promotion is a deterministic projection of Traces the conversation already recorded — it starts no model and writes no new Trace event, because the Note file is itself the evidence, so the closed Trace Vocabulary (ADR 0059) is untouched.

One conversation maps to one Note, and re-saving the same conversation overwrites that Note in place rather than minting a new file each time. This is what lets a Note grow as the user keeps asking questions. The Note is located by its `conversationId` in frontmatter, never by file name, because the title — and therefore the file name — is editable. The overwrite is guarded: the recorded `contentHash` is taken over the Note body alone, so recomputing it from the file on disk reveals any hand edit. If the file still matches its recorded hash it is overwritten (via a temporary file and atomic `rename`); if it does not, the save is refused and nothing is written. This preserves the real intent behind the Session-derived Note's never-overwrite semantics — those Notes are "human-facing Markdown artifacts" a user edits by hand — while still letting an untouched conversation Note track its conversation. A refused save is a deliberate dead end: the user must rename or remove the edited file themselves, so both the CLI message and the Side Panel result name the path and the recovery. Because the two paths must stay in lock-step, the Browser Workbench save depends on the `knowledge` module (`browserWorkbench` → `knowledge`, never the reverse), which owns the Note file format for both callers.

## The workspace selector does not overstep

Promotion has to know which workspace to write into, and the answer must be decided when the conversation is launched, not when it is saved. A Knowledge Note's `sourceSessionId` only resolves inside the workspace that holds the Session Traces (`<workspaceRoot>/.forgelet/sessions/`); choosing the workspace at save time — after the Sessions have run elsewhere — would write a Note whose provenance dangles and which `forge explain` cannot trace back. So the Side Panel gains a Workspace Profile selector, symmetric with the existing output-language selector: it is sticky in `chrome.storage.local`, it takes effect on the next launch, and it never re-runs the current attempt.

This does not violate the ROADMAP constraint that the browser "cannot select a model, path, or command." That constraint guards against the browser choosing an *arbitrary* target. The selector chooses among Workspace Profiles that were already approved on the CLI (`forge browser profiles approve`); the approval — the actual grant of authority over a path — happened in the terminal, not the browser. Picking one profile from an already-approved set is not selecting a path any more than the language selector is selecting a model. Recorded here explicitly because, without the distinction stated, a future reader would reasonably read the selector as a breach.

## Consequences

- The never-overwrite behavior of Session-derived Notes (`forge notes create --from-session`) is unchanged; only the conversation path uses the hash-guarded in-place overwrite.
- `saveKnowledgeNote` is a new top-level Native Host message carrying its own `version: 3` field, validated by a dedicated validator that reuses `BrowserProtocolValidationError` and the existing rejection codes plus `note_conflict` and `conversation_not_found`. `BROWSER_PROTOCOL_VERSION` is not bumped: its version gate only ever guarded `browserInvocation`, and a new extension against an old host still gets the same clean recovery text. Saving uses one-shot `sendNativeMessage`, not the streaming `connectNative` channel, because saving is not incremental.
- The Note frontmatter gains `conversationId`, `rootSessionId`, and `headSessionId`; `sourceSessionId` is kept and set to the root Session id so the existing `notes search` reader keeps working unchanged.
- The CLI resolves a bare `conversationId` to its root and current head by scanning workspace Traces; the head is the latest completed Session in the conversation, so a later successful retry supersedes the attempt it replaced. `--from-conversation` and `--from-session` are mutually exclusive.
- CONTEXT.md admits a narrowing: the Page Brief was described as "for fast page understanding rather than study," and promoting a whole conversation treats that chain as worth studying. The narrowing is intended, and the new **Knowledge Note** vocabulary entry records the widened source definition.
- Note-search quality over the longer, Evidence-bearing bodies is not yet validated. Judged not to block this slice.
