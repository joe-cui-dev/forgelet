# Forgelet Stays on Chat Completions

DeepSeek's 2026-07-31 V4 Flash release natively supports the Responses API format and ships a Codex integration, and Responses is where DeepSeek is visibly investing. We decided not to adopt it, and record the decision because a reader six months from now will see the provider's direction and assume Forgelet simply had not got round to it.

Nothing Forgelet needs is on the other side. The Responses API is stateless — no `previous_response_id`, conversations, or storage — which is neutral here because Forgelet already owns and replays its own Session state. Provider Carryover behaves the same in both formats and DeepSeek supports encrypted reasoning content in neither, so ADR 0065's problem is not solved by switching. The two capabilities Responses adds are ones Forgelet must refuse on principle rather than defer: server-side `web_search` would bypass the enforced egress scope of ADR 0037 and the Session Source Ledger of ADR 0038, and the freeform `apply_patch` custom tool would bypass the Permission Policy and `maxPatchBytes`. Meanwhile the cost is real: the Responses stream terminates with `response.completed`, `response.incomplete`, or `response.failed` and never sends `data: [DONE]`, which the current parser treats as a fatal condition, so adoption means a second stream grammar and a second set of terminal semantics to test.

We rejected adding an abstraction seam in anticipation, because `ModelClient.createTurn` is already that seam and a second one would be speculative. ADR 0066's effort enum was chosen in DeepSeek's Responses shape, so the translation cost is already prepaid should this be revisited. One claim is left open rather than assumed: DeepSeek describes 0731 as adapted for Codex, which could mean the model behaves better against Responses-shaped tool protocols. That is an empirical question, and it belongs in the provider compatibility suite as a measurement — the same task run through both protocols — not in an architectural decision made in advance of evidence. The `data: [DONE]` requirement is meanwhile annotated as a Chat Completions assumption rather than left welded into the generic parse path.
